# Temporal engineering memory (Phase H3)

Versioned, evidence-backed memory for decisions, bugs, fixes, test evidence and rejected approaches. It is **not** chat storage: every record points at real, indexed source and history, says who proposed and approved it,
and is judged against the CURRENT code, branch and environment every time it is read. Schema: migration v6. Nothing here calls a model or the network.

## Records
Kinds: `observation`, `claim`, `decision`, `finding`, `bug`, `fix`, `test_evidence`, `rejected_approach`. A record has: title, body (text only, never source), origin (`human | model | ci | import`), proposer, approver/verifier, status
(`candidate | approved | verified | stale | rejected`), the **evidence object**, an **applicability scope**, **invalidation predicates**, and bindings (revision, branch, generation, dirty overlay at recording).
**Evidence object:** a claim; typed pointers (`file`, `symbol`, `feature`, `test` (with case title, optionally the failing test), `commit` with a role (`introduced | fixed | verified | related`), `requirement`, `incident`, `artifact`), each bound at recording to the content hash it pointed at;
evidence type and method; the test environment; artifacts (names and hashes). Pointers must resolve (a file in the published index, a symbol, a feature entity, a test case, a commit in the history ledger): a record cannot point at things that are not there.
**Two time axes, independent:** `valid_from/valid_to` (when the statement is true in the world) and `recorded_at/superseded_at` (when the store learned it, and when a later record replaced it). A CI result that finishes Monday and is recorded Wednesday has `valid_from` Monday and `recorded_at` Wednesday; `memory search --as-of-valid T --as-of-recorded R` answers "true at T, as known at R".
**Immutable:** content columns cannot be changed (a trigger refuses it); only standing (status, approval, supersession) moves, along legal transitions only (an approval, a verification, a supersession or a rejection reason can be set once and never rewritten; a rejected record stays rejected), each transition leaving an immutable event (events of an existing record cannot be deleted). Each record's content hash is recomputed on read: a record whose stored content no longer matches is `unknown`, never trusted. Corrections are new records that `supersede` the old one; both are kept.

## Rules enforced at write
- Everything arrives as `candidate`. Model, CI and imported records are never authoritative by themselves; a human-proposed record also needs an approving operator (optionally a DIFFERENT operator: `memory operator distinct on`).
- Approval needs a source pointer, evidence that currently applies, and at least one invalidation predicate (only bugs and fixes, which are historical, may have none: an empty predicate set would mean the record never goes stale). Model-derived content (declared origin `model` OR evidence type `model_inference`) additionally needs independent substantiation: a link `substantiated_by` to an approved or verified record from a DIFFERENT proposer, not itself model-derived, that points at the same source and still applies; if that substantiation later goes stale, the record loses its authority. A fix cannot be approved before the bug it fixes. `verified` needs test or CI evidence with a test pointer and a `test_present` predicate, and (under the two-person rule) a verifier who is neither proposer nor approver. Superseding an approved or verified record needs the approve role.
- A **fix** needs a traceable incident (a bug record it `fixes`, or an incident pointer) or a failing-test pointer, AND a fixing commit (role `fixed`) that is in the history ledger. A bug needs an incident, test or commit pointer. A rejected approach must give its reason.
- EVERY stored string (title, body, claim, origin detail, evidence method, environment keys and values, artifact names, pointers, scope, predicates, references, reasons) is scanned, also in `key: "value"` form, and refused if the secret scanner flags it; the export re-scans every field and withholds a record that trips it. Text is also refused and refused if it carries control or invisible formatting characters. A `validFrom` in the future is refused.

## Does a record still apply? (computed at read time, never trusted from a flag)
`superseded`, `expired`, `ended` (its own windows) | `out_of_scope` (its revision is in the ledger but is not an ancestor of the current checkpoint: another line of history) | `unknown` (no checkpoint, its revision is not in the ledger, no index, an environment value never recorded) | `stale` (an invalidation predicate fails) | `applies`.
Predicates: `source_hash` (the file, symbol signature or feature entity it pointed at changed or vanished), `test_present` (the required test file or case was changed or deleted), `environment` (an assumption's recorded current value differs). Defaults: pointers bound to source get `source_hash`, test pointers get `test_present`; **bugs and fixes have none** (they are historical facts about commits that stay true after the code moves on).
Unknown is never treated as applies. **Retrieval is safe forgetting**: by default only records that are approved or verified AND apply are returned; candidates (including every model proposal), stale, unknown, other-branch, expired, superseded and rejected records are excluded and COUNTED, and can be asked for explicitly with a label and the reason. A dirty working tree is judged as the working tree (its edits change the hashes) and the answer carries a warning. Switching branches never inherits another branch's record (`out_of_scope`); each worktree has its own store.
`memory stale` lists what no longer applies and why; `memory stale --record` (an operator) writes one `invalidated` event per record and checkpoint; it does NOT change stored statuses (standing is computed on every read), so invalidating on a descendant branch cannot damage a record for the branch it was made on.

## Who may write
**Writes are privileged CLI operations; MCP and repository text can never write.** An operator is a named principal with roles (`propose`, `approve`, `verify`, `admin`) and a secret token kept only as a SHA-256 in `.engineering-brain/operators.json` (mode 0600). The CLI authenticates from `ENGBRAIN_OPERATOR` and `ENGBRAIN_OPERATOR_TOKEN`. The first operator becomes an admin and can be created without a token only with an explicit `--yes` (a deliberate local act); later ones need an admin. `operator revoke <id>` and `operator rotate <id>` (an admin, or the operator for its own token) exist; the last admin cannot be revoked; changes to the operator file are serialised with a lock. README text, commit messages and record bodies are data: nothing reads them for policy (tested).
**Limit, stated plainly:** this is local token authentication. It stops an agent that only has MCP access or repository text; it does not stop a hostile process running as the same OS user that can read the operator's environment or token. Stronger identity (keychain, hardware keys) is out of scope.

## Reading
`engbrain memory search | show | stale | summary | env list | export`, `engbrain bugs related --file|--symbol|--feature` (bugs with their fixes and the standing of each fix's verification: a stale verification is shown as stale, not hidden), `engbrain decisions related ...` (decisions and rejected approaches, which keep their reason and dates), `engbrain evidence provenance <id>` (each pointer's recorded and current hash, each predicate's result, commits, proposer, approver, events).
MCP (read-only): `search_memory`, `retrieve_related_bugs`, `retrieve_architecture_decisions`, `get_memory_provenance`. Historical views (`--as-of-valid`, `--as-of-recorded`, strict ISO-8601 UTC timestamps; a calendar-invalid time is refused) show the status the store KNEW then, from the event log, and are never authoritative. The authority filter runs in SQL before the scan window, so a flood of candidates cannot crowd approved records out; one reachability walk serves a whole query. CLI reads warn on stderr (and report `indexFreshness` in JSON) when the index is behind HEAD or the working tree, and refuse with `--fail-on-stale`. Every query is bounded by a token budget (the whole response including its metadata), lists evidence paths, and is deterministic: a fresh process returns the same results. `memory summary` produces a compact cross-session list (`id@revision kind [status] title`) that references records by id and never re-inserts bodies.
Retention: observations expire (default 90 days); `memory gc` (admin) deletes expired observations that no approved or verified record links to; decisions, bugs, fixes, test evidence and rejected approaches are never expired by GC. `memory export` withholds (and counts) any record whose text trips the secret scanner and contains hashes and pointers, never source text.

## Relation to H2 claims
`feature claims` (H2) remain for statements about discovered features; memory records are the general, bitemporal store and can point at feature entities.

## Measured (synthetic, macOS, Node 22.23.3 as darwin-x64; `node tests/bench/memory-bench.mjs <records> <dir>`)
10,000 records over 50 files (half approved): writes 4,300/s (each approval evaluated), search p50 25 ms / p95 33 ms, summary 25 ms, `bugs related` 1 ms, `memory stale` 16 ms, DB 11 MiB, peak RSS 290 MiB. A search over 2,100 candidates plus a 40,000-commit ledger completes in a few seconds (tested). Not measured: real repositories, cold cache, other platforms.

## Independent review fixes
A fresh read-only Claude agent (not Codex) confirmed 13 defects, all fixed with regression tests (`tests/acceptance/h3-memory.test.ts`, section "H3 review regressions"): per-record reachability walks, the scan window filled before the authority filter, a proposer retiring approved records, model-derived content approved without relevant independent substantiation, secrets in non-title fields and predicates, empty invalidation, historical views claiming authority and accepting any time string, cross-branch demotion by `stale --record`, substring scope matches, dangling links after GC, silently shifted dates, no freshness check on CLI reads, and operator gaps (no revoke/rotate, unconfirmed bootstrap, two-person rule not applied to verification). Plausible items handled: fix commit ordering and bug status, feature pointers with null hashes, future `validFrom`, C1 control characters, escaped key echoes, locking, trigger-guarded transitions, integrity re-check. The post-fix state was not re-reviewed.

## Known limits
File-granular invalidation (a changed file stales its records; symbol checks add existence and signature); `valid_to` cannot be corrected in place (supersede instead); a record that went `stale` stays stale after its evidence is restored (re-record it); branch lineage needs the history ledger (`engbrain refresh`); macOS/Node 22 only.
