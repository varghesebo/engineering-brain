# Feature and capability graph (Phase H2)

A deterministic, versioned graph of feature-shaped things in a snapshot and how they connect across files, packages and services. It is **not** a generated encyclopedia and not
business knowledge: every entity and edge says how it was found and how certain it is, dynamic behaviour stays explicitly unknown, and nothing is inferred from a name alone.
Schema: migration v5. Built per generation, after the source graph, under the same writer lock and published with the generation.

## Entities (`feature_entities`, one set per generation, immutable once published)
`route` (HTTP server route), `api_call` (client request), `api_operation` (an OpenAPI/Swagger JSON operation), `event` (producer or consumer of a message, topic or queue), `ui_route`, `db_table`, `db_query`, `job` (cron or worker), `test` (a test file with its case titles).
Every entity records: kind, role, normalised key (`GET /api/users/{}`, an event name, a table), path and lines, package/service directory, **mechanism** (`route_pattern`, `decorator_pattern`, `client_call_pattern`, `messaging_pattern`, `ui_route_pattern`, `sql_ddl`, `sql_literal`, `orm_pattern`, `job_pattern`, `openapi_spec`, `file_convention`, `test_pattern`), **certainty** (`static`: identity is a literal; `heuristic`: a weak signal such as a path-looking call on an unknown receiver; `dynamic_unknown`: the path or name is not a literal), trust (`discovered`), the content hash of its source and the generation since which it has existed (`valid_from_generation`).
Facts are **content-addressed and path-free** (`fact_entities`, extractor `feature:entities` v1); the path-dependent work (mount prefixes, packages, file-convention routes, linking) happens per generation. Detection is a bounded lexical scan (comments, strings, templates and regex literals are understood; JSX text cannot swallow a file), not a full parse, and says so through certainty.
Adapters in this build: Express/Fastify/Koa-style calls, NestJS decorators, Next.js `pages/` and `app/` file conventions, `fetch`/axios-style clients, emit/publish/subscribe/consume/process and `new Worker`, cron schedulers and `new CronJob`, React Router JSX and route objects, SQL (`CREATE TABLE` DDL and `SELECT/INSERT/UPDATE/DELETE` in `.sql` files and string literals), `prisma.<model>.<op>`, `describe/it/test` titles, OpenAPI JSON. OpenAPI YAML is reported as an `unsupported_spec_format` gap (no YAML parser is bundled).

## Edges (`feature_edges`) and what each means
`HANDLES_WITH` / `RENDERS` / `CONSUMES_WITH` / `RUNS` (entry point to its handling symbol: declared in the file, imported, or a namespace member), `CALLS_API` (client call to route by exact method and normalised path; `ambiguous` when several routes match; `ANY` routes accept every method), `USES_API_CALL` (a UI route's component file, or files it imports, contains the call), `EVENT_FLOW` (producer to consumer by identical literal name), `PUBLISHES` / `QUERIES` / `CALLS_API_FROM_HANDLER` (the call lies inside the handler's source range), `READS` / `WRITES` (query to table), `TESTS` (a test file imports the file: **not** evidence it exercises it), `DOCUMENTS` (a spec operation matches a route). Every edge carries certainty (`resolved | ambiguous | heuristic`), mechanism, reason and the source file and line that justify it.
Mount prefixes (`app.use("/api", router)`) are applied statically through resolved imports, only to the router object that was actually mounted (middleware and other routers in the same file get nothing; `mount_target_not_a_router` is reported), to a depth of three (`mount_chain_too_deep`), at most four effective paths per route (`too_many_mount_paths`).
Certainty rules that matter: a client call is `resolved` only for a single route with an exact method and path from a known client; a parameter segment match, an unknown method (`fetch(url, opts)`), several candidate routes, a configured `baseURL`, a weak client signal or a non-messaging event receiver give `ambiguous` or `heuristic`; calls to another host are never linked to internal routes; a table is `resolved` only where its DDL is in the same package (otherwise `heuristic`/`ambiguous`), ORM model access is always `heuristic`; a handler named by an import is the import, not a same-named class method.

## Coverage gaps (`feature_gaps`)
Reported, never hidden: `dynamic_route`, `dynamic_client_call`, `dynamic_ui_route`, `dynamic_event_name`, `client_call_without_route`, `event_without_consumer`, `event_without_producer` (only for messaging-style receivers or namespaced names, to avoid DOM-event noise), `handler_not_resolved`, `table_without_schema`, `spec_operation_without_route`, `route_not_in_spec`, `unsupported_spec_format`, `mount_target_not_a_router`, `mount_chain_too_deep`, `too_many_mount_paths`, `detection_truncated` (a file hit a safety limit), `entity_limit_reached`, `edge_limit_reached`. Nothing is dropped silently.

## Features
- **Discovered flows**: for every route, UI route and job, the bounded neighbourhood over feature edges (4 hops, fan-out and member caps, `truncated` flagged). Id `flow:<kind>:<key>@<service directory>` (the service qualifies it, so the same route in two services is two features; a same-service duplicate is told apart by file path, never by an order-dependent counter). A flow follows a REQUEST: down along forward relations, up only to the callers of the entry point, with tests and documentation attached; a shared table or consumer never pulls sibling routes in, and a hub (more links than the fan-out cap) is a member that is not expanded. Labelled a candidate grouping, not a business-defined feature.
- **Annotations**: user-authored JSON in `.engineering-brain/features/*.json` (a local, gitignored directory; never the repository tree), strictly validated (schema version 1, closed property sets, size and count limits, no symlinks, no traversal). They describe members by selector and carry documented constraints with their source. They are applied at READ time and create no entity or edge: a member the code does not contain stays `documented_but_not_found`, and constraints are shown as documented, not verified.
- **Claims** (`feature_claims`): candidate statements, typically from an optional local model analysis the user approves (`feature propose --from-file ... --source model --source-detail <model>`). They are always `candidate` and labelled inferred/proposed; a claim is identified by the hash of its normalised statement TOGETHER WITH its evidence references, so repetition from any source changes nothing, while the same statement with different evidence is a separate claim (nobody can squat a statement with bogus evidence); a retired claim can be proposed again; a proposal may carry only a statement and evidence references (anything else is rejected); evidence must exist in the current generation. `feature approve <id> --by <person> --yes` is a human act: it needs live evidence and the approver must differ from the proposing model (identity is asserted, not authenticated). Evidence is fingerprinted at proposal time: when it changes or disappears the claim shows `evidence_changed` / `evidence_missing`; approval is REFUSED on changed evidence until a person re-binds the candidate (`feature rebind <id>`), and an approved claim is never silently re-bound. Staleness is file-granular for code entities and statement-granular for tables (the hash of the `CREATE TABLE` text; a referenced-only table takes the hash of the queries that reference it). Claim text, approver and source may not contain control or invisible formatting characters. **Approval identity is asserted, not authenticated**: a local process that can run the CLI can claim any name; the controls are procedural (an explicit `--by` and `--yes`, required live evidence, a model cannot approve under the name it proposed with, no automatic path, no model call in engbrain), not a guarantee against a hostile local agent. No model is ever called by engbrain.

## Identity over time (`feature_lineage`)
Between consecutive generations ON THE SAME BRANCH (a branch's first generation has no predecessor and claims nothing; validity `valid_from_generation` is likewise per branch), by HANDLER identity (path + qualified name), never by name: `renamed` (the entry point's handler is unchanged), `split` (one handler now serves several features), `merged` (a feature now contains the entry-point handlers of several removed ones), `ambiguous` (overlap that fits none of these: reported, not guessed), `added`, `removed`. All but `added/removed` are `heuristic` or `ambiguous`, never `resolved`. History is as deep as the retained generations; features are version-scoped to the snapshot (worktree, branch and dirty state each have their own generation), and different branches are never mixed.

## Queries (bounded, read-only, one snapshot per call)
`engbrain feature list | show <id> | trace <entity> [--direction] [--depth] | impact --file|--symbol | provenance <id> | gaps | claims | propose | approve | retire | validate`. Entities are named by id, `kind:key` (`route:GET /api/users`), `file:path` or `sym:path#name`. Traversals cap depth (6), nodes (300), edges (800) and per-node fan-out (60) and report which cap truncated them. Nothing is exposed over MCP in this build.

## Independent review fixes
A fresh read-only Claude agent (not Codex) confirmed 19 defects: wrong mount prefixes, cross-service table and event links marked `resolved`, external hosts linked to internal routes, a guessed `fetch` method, NestJS prefix errors, template-literal paths treated as static, receiver false positives, SQL-in-prose false positives, wrong handler resolution, over-linked UI routes, undirected flows, Next.js conventions without Next, feature-id collisions, lineage and validity mixing branches, line-dependent entity ids, line drift, silent truncation, stale evidence laundered by approval, DDL evidence that never went stale, evidence squatting, quadratic SQL and unclosed-call scans, mount fan-out amplification, extension-class poisoning of facts, and raw URL literals in facts. All were fixed with regression tests (`packages/core/test/featureDetectors.test.ts`, `tests/acceptance/h2-review.test.ts`); the post-fix state was not re-reviewed.

## Limits (honest)
Lexical detection can miss unusual styles (JSX text containing `//` still swallows the rest of its line; `axios({url})`, `axios.request` and `useRoutes` are not detected and not reported); a router imported under a name the importer chose is matched through resolved imports only; evidence staleness for routes and handlers is file-granular; lineage is heuristic; Lexical detection can also mis-read code-looking text and can mis-attribute code-looking strings; a path-looking call on an unknown receiver is only a weak client hint. Event matching is by identical literal name only. Test edges mean "imports", not coverage. No call graph exists, so a handler's downstream effects are found only inside its own source range. Cross-service links exist only when the services are in the indexed repository. TypeScript/JavaScript, SQL and JSON only. macOS/Node 22 only; Linux, Windows and Node 24 untested.
